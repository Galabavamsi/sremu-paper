\section{Design}\label{sec:design}

\subsection{Architecture}\label{sec:design-arch}
% sremu/api/device.py (Device.inproc, Device.connect, Device.from_engine; EngineProtocol of
% contracts.py); sremu/engine/emulator.py; sremu/transport/{control_server,zmq_native,
% rawreqrep}.py; sremu/commands/serve.py (served runs, --paused default); sremu/record/*.
\claim{C-ARCH}The engine computes the samples of every receive (RX) stream from the samples of
every transmit (TX) stream, the propagation model and the RIS configurations in force
(Appendix~\ref{app:interfaces} draws the processes and planes). It runs
inside the Python process of an application (\texttt{Device.inproc}) or as a served process
reached through sockets (\texttt{Device.connect}); both forms implement one engine interface,
and a run whose TX and RX applications are separate operating-system processes gives the
same RX samples, bit for bit, as the same run in one process (IO-02).
\claim{C-PLANES}A served engine uses ZMQ sockets~\cite{ZeroMQ}: a framed IQ data plane (one
ingress socket for TX applications, one egress socket per RX stream), a raw request--reply data
plane (Section~\ref{sec:design-if}), a control plane of JavaScript Object Notation (JSON)
requests on one \texttt{ROUTER} socket (by default \texttt{\txtControlEndpoint}), which also
carries the barrier messages of registered controllers, and a \texttt{PUB} socket for
telemetry. \claim{C-RECORDING}A recorder writes a manifest, the resolved scenario, an event
log of every command record and, optionally, SigMF recordings~\cite{SigMF} per run.
\claim{C-IMPL}\sremu{} is a Python package (Python \txtPythonReq{} or later; \numSrcModules{}
modules, about \numSrcKloc{} thousand lines) built on NumPy and SciPy, with a NumPy reference
backend and a compiled numba backend for rendering, pyzmq for the sockets~\cite{ZeroMQ} and
pydantic for validation; Gymnasium and SigMF are optional~\cite{Towers2024Gymnasium,SigMF}. It
runs on Windows and Linux.

\subsection{Time model and command semantics}\label{sec:design-time}
% sremu/timebase.py: R1-R5, to_ticks, count, page_size; DEFAULT_PAGE_TARGET_S, PAGE_MIN/MAX.
% engine/scheduler.py (advance_group, JobBuilder.render_range), D-1..D-6; channel/interp.py.
\claim{C-TIMEBASE}Sample rates and virtual times are exact rational numbers, and sample~$0$
of every stream is at $t=0$. A time maps to a sample as $\mathrm{to\_ticks}(t,f)=\lfloor
tf+1/2\rfloor$, the nearest sample with ties rounded up as in UHD~\cite{UHDManual}, and a
stream produces $\lceil t_1f\rceil-\lceil t_0f\rceil$ samples on $[t_0,t_1)$ for any mix of
rates (RT-01, RT-02); wall-clock time never enters data-plane arithmetic (RT-15).
\claim{C-INVARIANCE}Each RX stream is processed in pages of about \numPageTargetMs~ms on an
absolute grid, cut at snapshot boundaries, switch samples, barrier limits and the end of TX
input (Fig.~\ref{fig:F2}(a)). Per-sample quantities are closed-form functions of the absolute
sample index, and sums run in a fixed order, so the RX samples are identical bit for bit
however clients chunk their calls, wherever events cut a page and, in deterministic mode (the
default, Appendix~\ref{app:interfaces}), whatever the thread count (RT-03, RT-10).

\paragraph*{RIS commands}
% engine/commands.py (switch time at the RIS, per-RX per-tile k_{r,j}, time forms, late
% policies, ties, counterfactual enable timeline, transitions as Mixture); contracts.py
% CommandRecord and config_hash (blake2b-128 of int16 states + enable byte).
\claim{C-TIMED-CMD}A RIS command carries a switch time $t_{\mathrm{sw}}$ defined at the
surface. Receiver $r$ sees the change on the paths of render tile $j$ at sample
\begin{equation}
k_{r,j}=\mathrm{to\_ticks}\bigl(t_{\mathrm{sw}}+\tau_{r,j}(t_{\mathrm{sw}}),\,f_r\bigr),
\label{eq:kr}
\end{equation}
where $\tau_{r,j}$ is the propagation delay from the reference point of tile $j$ (the panel
centre for an untiled panel) to the receiver in the geometry at $t_{\mathrm{sw}}$ (RT-05), so
receivers at different distances see one switch at different samples (Fig.~\ref{fig:F2}(b)).
The time of a command is an exact surface time, a sample of a named RX stream, or `as soon as
possible' (asap), the earliest time that every receiver can still honour.
\claim{C-LATE-CMD}The frontier of a receiver is its earliest uncomputed sample, and a command
is late when a switch sample falls below a frontier. The default policy,
\texttt{apply\_on\_arrival} as in UHD, moves the switch to the single surface time
$t'=\max_{r,j}(\mathrm{frontier}_r/f_r-\tau_{r,j})$ and maps every receiver again
with~\eqref{eq:kr}, so all receivers still see one physical switch; the policy
\texttt{reject} returns \texttt{LATE\_COMMAND} and applies nothing (RT-06).
\claim{C-RECORDS}Each command yields one record with requested and applied surface times and
samples per receiver, their difference (the lateness), wall-clock receipt and delivery times,
status and a hash of the applied configuration (Appendix~\ref{app:interfaces}).
\claim{C-TRANSITIONS}A reconfiguration need not be instantaneous: changing elements form
transition classes with profiles $g_c$ (a step, the default; a linear ramp; or an
exponential), and because $\mathrm{combine}$ is linear in $\Gamma$ the channel is exactly
$h(t)=h_{\mathrm{old}}(t)+\sum_c g_c(t-t_{\mathrm{sw},r})\,\Delta h_c(t)$, with each change
$\Delta h_c$ interpolated like any path, also under mobility (RT-12). The default duration is
the panel's \texttt{reconfiguration\_time\_s}, named after a GS RIS 008
parameter~\cite{ETSI_GS_RIS008}; the
complex-linear path between states is an engineering choice (ENG).

\paragraph*{Controllers in the loop}
% engine/barriers.py (t_b = m T_c, limit to_ticks(t_b + L_min), observation before
% to_ticks(t_b), latency = fixed + keyed jitter, LookaheadViolation), engine/emulator.py
% (_observation), transport/control_server.py (remote ctrl.barrier / ctrl.ack),
% control/remote.py (run_remote).
\claim{C-BARRIERS}A controller registers with a period $T_c$ and a minimum latency
$L_{\min}$. At each barrier $t_b=mT_c$ the engine computes every receiver up to sample
$\mathrm{to\_ticks}(t_b+L_{\min},f_r)$, exclusive, and then gives the controller an
observation built from samples before $\mathrm{to\_ticks}(t_b,f_r)$, such as each receiver's
measured power. Actions take effect at $t_b$ plus a latency drawn
from a keyed model and never smaller than $L_{\min}$; an earlier action raises
\texttt{LOOKAHEAD\_VIOLATION} (RT-17). The frontier limit and~\eqref{eq:kr} use the same
monotone rounding and $\tau_{r,j}\ge0$, so these actions are never late and the time a
controller takes to decide changes no RX sample, in process or remote (RT-08): the lookahead
rule of conservative parallel discrete-event simulation.

\paragraph*{Lockstep, paced and batch operation}
% engine/streams.py (TX commitment), engine/scheduler.py (wait on TX), engine/emulator.py
% (stall report, nondeterministic_inputs, coupling matrix in EngineConfig), engine/pacer.py
% (release R_j, hybrid sleep, slacks), streams.py (TIME_ERROR, underflow, overflow pages);
% engine/batch.py (run_batch); record/replay.py.
\claim{C-LOCKSTEP}In lockstep mode virtual time advances as far as the inputs allow: a TX
stream is committed through sample $K$ when its samples cover $K$, its last burst ended, or it
announced idleness up to $K$ (\texttt{idle\_until}, an extension of the UHD interface). Runs
with barrier controllers are deterministic; other timed commands are deterministic when they
arrive on time, and otherwise the manifest flags nondeterministic inputs.
\claim{C-PACED}In paced mode, page $j$ is released at wall time
$R_j=t_0+k_1/f+D_{\mathrm{lag}}$, with page end $k_1$ and an input slack $D_{\mathrm{lag}}$;
late inputs are dropped, missing samples become zeros and a slow RX client loses pages, each
with a report, and deadline misses are counted (RT-18). Paced mode is soft real time: it counts misses rather
than assuming their absence, and it admits asynchronous controllers, whose commands carry
measured lateness. \claim{C-BATCH}A batch path (\texttt{run\_batch}) evaluates
$\mathrm{combine}(\mathrm{snapshot}(t),\mathrm{cfg}(t))$ on a time grid without IQ samples, with
the same model, command semantics (switches at their surface time), controllers and random
keys; in a static scene with noise off, an in-process controller and no signaling delay, its
time-averaged received power equals that of the IQ path within a relative \numVaFourRelTol{}
(VA-4). Holding each step at its start value, it reads up to \numVaOneLeftMaxDb~dB high under
mobility with a delayed controller, beyond the \numVaOneTolDb~dB limit of VA-1, so E-A uses a
midpoint evaluator (Section~\ref{sec:cases-ea}). \claim{C-REPLAY}A replay re-injects the recorded TX
streams and commands at their applied times and reproduces the recorded RX samples bit for bit
(RT-16).

\subsection{Interfaces}\label{sec:design-if}
% api/device.py, api/streams.py, api/metadata.py (codes, modes, table_iii), compat.py;
% the API table (generated by tools/gen_tables.py) is in Appendix B.
\claim{C-API}The Python API follows UHD~\cite{UHDManual} without binary compatibility: streams
carry UHD-style metadata with exact time specifications, failures are status codes (IO-06),
and RIS commands carry state indices, phases or a codebook index, an optional transition and a
late policy. Each stream has one channel, and an unmodified UHD application does not run
against this interface (Section~\ref{sec:future}). \claim{C-CONTROL}Control messages are
validated before dispatch, so every refusal has one code, and a socket command lands at its
exact sample with zero lateness in lockstep mode (IO-03). \claim{C-SECURITY}Sockets bind to
loopback addresses unless remote binding is allowed; there is no authentication (IO-04).
\claim{C-RAW}For radio software that exchanges raw samples over request--reply sockets, the
engine takes the broker role of the srsRAN ZMQ setup~\cite{srsRANZMQ}: it requests TX samples
from the peer and answers its receive requests, with timing implicit in sample counts, so the
mode is lockstep. Its two request formats were taken from the srsRAN 4G and GNU Radio sources
and are tested against stub peers (IO-08); unmodified GNU Radio \txtEeGrVersion{} runs against
it (Section~\ref{sec:cases-ee}). No srsRAN binary has been run, so we call it an srsRAN-style
raw-IQ mode.

\subsection{Element response tables}\label{sec:design-states}
% physics/response.py (ResponseTable, Provenance, validators, from_csv, from_matlab_scurve,
% from_state_library, sample, half_difference extension), physics/tables/*.yaml (built-ins),
% contracts.RisCapabilities (GS RIS 008 names).
\claim{C-TABLES}Element responses are tables $\Gamma(s,f,\theta_i,\theta_s)$ over state,
frequency, and signed incidence and reflection angles in one plane of incidence
(Appendix~\ref{app:model}), read at the carrier, with mandatory provenance such as the kind of
source, uncertainties and a hash of the raw data.
\claim{C-TABLE-CHECKS}Validators reject tables that are not passive, not reciprocal or too
coarse, and queries outside the grid or band (PH-31); interpolation is complex-linear, so the
channel stays linear in $\Gamma$. \claim{C-TABLE-IMPORT}Tables come from CSV files with a
provenance sidecar, MATLAB unit-cell curves or built-in alphabets, including the published
states of Tang et al.~\cite{Tang2022mmWave}. \claim{C-CAPS}Panel capabilities carry the names
of GS RIS 008 parameters~\cite{ETSI_GS_RIS008} where they exist (Appendices~\ref{app:survey},
\ref{app:interfaces}).
